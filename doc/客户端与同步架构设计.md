# 桌面客户端与双向同步：架构设计（v2 · 重排版）

> **目标**：把 api-doc-go 当**服务端（协作 + 同步中心）**，另做一个 **Wails v2 桌面客户端**：接口集合以**文件方式**管理（纯文本文件、git 友好），可**单机离线使用**，联网时**双向同步**。
> **代码组织**：客户端是**独立代码库**，不复用/不打包现有 Web 前端；两侧共享「Go 纯逻辑模块 + 契约 + 文案」。
> **文档状态**：v2（2026-09-27 重排版）。v1 按讨论时间自然生长，本版**重组结构、去除已被推翻的内容**，并在 **§5.9 给出对同步逻辑的批判性评审（9 项发现，2 项设计修正已采纳）**。
> 证据引用 `路径:行号`，基于 2026-09-26/27 的仓库现状。

## 2. 总体架构

```
  ┌──────────────── 客户端仓库（独立代码库，Wails v2，本地优先） ────────────────┐
  │  自建 Vue UI：多请求 TAB + 默认直接可编辑 + 发送/响应/历史/同步状态          │
  │  ┌──────────────┐   ┌───────────────┐   ┌──────────────┐   ┌────────────┐   │
  │  │ 集合文件层    │◄─►│ 本地索引 SQLite│   │RequestRunner │   │ SyncEngine │   │
  │  │ (文件=真相源) │   │ (可重建/搜索)  │   │ 变量渲染+发送 │   │ pull/push  │   │
  │  └──────────────┘   └───────────────┘   └──────────────┘   └─────┬──────┘   │
  │   ▲ fsnotify（自写回环抑制）            ▲ 断言/脚本沙箱           │          │
  └───┼────────────────────────────────────┼─────────────────────────┼──────────┘
      │          ┌─────────────────────────┴───────┐                 │
      └─────────►│ 共享纯逻辑 pkg/*（同一份实现）    │◄────────────────┘
                 │ collection / varx / codegen /    │            HTTP(S)：PAT +
                 │ openapi / postman（无gin·无gorm） │            增量协议（可离线积压）
  ┌──────────────┴─────────────────────────────────────────────┴──────────────────┐
  │ 服务端仓库（现有项目）= 同步中心 + Web 协作 UI                                   │
  │  /api/sync/*（revision·change_log·批量 push）+ 现有 CRUD（Web 照用）          │
  │  /api/meta 能力协商 · PAT 令牌 · 可选请求代理（Web Try it）· Mock · 分享          │
  └────────────────────────────────────────────────────────────────────────────────┘
```

**两条铁律**
1. **文件是真相源，索引是缓存**：删掉索引能从文件重建；服务端自增 `id` 不进入文件语义，只写 `uid`。
2. **单机与联网是同一份代码**：单机 = 不登录不连服务端；联网 = 多挂 SyncEngine。没有"离线专用分支"。

**产品原则**（写进 README 与客户端文案）
> **服务端是「团队共享视图」的权威；客户端是「个人工作副本」的权威。**
> 冲突时：共享视图优先（服务端版本落回原文件），个人改动**永不静默丢弃**（总是另存 `.conflict-*`）。

## 3. 文件格式（本地集合 = 真相源）

### 3.1 目录布局

```
my-collection/
├── opencollection.yml          # 集合清单（Bruno 也认）：info/meta.uid/sync 段/format 版本
├── environments/
│   ├── dev.yml                 # 可提交：变量名/描述；secret 变量只留 `secret: true` 占位
│   └── dev.secrets.yml         # 不提交（git-ignored）：secret 变量的明文值
├── field-mapping.yml           # 字段映射字典（项目级）
├── docs/<doc-uid>.md           # 项目文档：Markdown + front-matter(title/icon/state/is_top)
├── assets/<sha256>.<ext>       # 内容寻址附件
├── <folder>/folder.yml         # 分组
├── <folder>/<request>.yml      # 接口
├── .trash/                     # 收到远端删除的文件副本（可恢复）
├── .conflicts/                 # 冲突副本目录（同步引擎忽略此目录）
└── .gitignore                  # environments/*.secrets.yml / *.local.yml / .trash/ / .conflicts/
```

### 3.2 文件 ↔ 实体映射

| 文件 | 服务端实体 | 关键映射 |
|---|---|---|
| `opencollection.yml` | `project` | `info.name`→Title；`meta.uid`→ExtUID；`sync:` 段（server_url/project_id/游标/last_synced_at） |
| `<folder>/folder.yml` | `group` | 目录层级→PID；`info.seq`→Priority；type（接口=1/文档=3） |
| `<request>.yml` | `api` | `http.method/url/params/headers`、`body(json)`→参数行、`docs`→Description、`settings/auth/vars/script/assert`→**`api.extra`（原样 JSON，服务端不解释）**、`meta.uid`→ExtUID |
| `environments/*.yml`(+`*.secrets.yml`) | `variable_env` + `variable` | 环境名/颜色/默认 → `variable_env`；键值 → `variable`（`secret:true`→IsSecret；明文值只在 secrets 文件） |
| `docs/<uid>.md` | `doc` | front-matter → 字段；正文 → Content |
| `field-mapping.yml` | `field_mapping` | 字段/类型/描述 |

> 实体依据：`model/project.go:6-12`、`group.go:12-19`、`api.go:5-26`（JSON 字段均为 `text`）、`variable.go:30-64`、`doc.go:13-27`、`business.go:70-76`。
> **兼容性**：`doc/api_docs/*.yml` 与 Bruno 请求文件同为 `info(name/type/seq)+http+settings+docs` 形状（现有导入器 `bruno.go:43-47` 可解析）；扩展字段 Bruno 会忽略 → **"Bruno 打开 → 本客户端编辑 → Bruno 再打开"不丢信息**（round-trip 纳入 P1 验收）。

## 4. 同步协议

### 4.1 概念与数据模型

| 概念 | 定义 | 落点 |
|---|---|---|
| **条目** | 同步的最小单位：一条 `api`/`group`/`doc`/`variable_env`/`variable`/`field_mapping`。**不是文件、不是字段** | 文件名/目录/排版只是本地呈现 |
| **`uid`** | 条目身份（客户端生成 UUID），离线新建/重命名/移动都不丢 | 文件 `meta.uid` ↔ 实体 `ext_uid`（局部唯一索引，排除软删行） |
| **`revision` / 游标** | 项目级"变更流水游标"，用于增量拉取 | **取 `change_log.id` 本身**（自增），不单独维护计数器（见 §5.9-A） |
| **`change_log`** | 变更流水，**只存指针**：`{id, project_id, entity_type, ext_uid, op: upsert|delete, actor, device, created_at}` | repository 写路径同一事务内落一条（覆盖 Web 与 sync 两个入口） |
| **条目版本 `item_rev`** | 条目最后一次变更的 `change_log.id`；**冲突检测的基线用它与客户端记录的 `base_rev` 比较**（评审改进，替代时间戳，见 §5.9-B） | 同步实体加列 `last_change_id bigint` |
| **tombstone** | 删除事件（`op=delete`），防止"离线端复活已删条目" | 软删时写 `op=delete` |
| **`op_id`** | push 幂等键（重试安全） | `sync_op` 表记录已处理的 op_id（保留 N 天） |
| **同步范围** | 上述 6 类实体 | 权限/成员/通知/日志/分享/备忘（v1）**不同步**；附件走内容寻址单独拉取 |

### 4.2 接口（全部挂现有鉴权 + 项目权限位）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/meta` | 能力协商：`{server_version, api_version, sync_proto, features, min_client_version}`。客户端连接时校验，不兼容则提示升级 |
| GET | `/api/sync/state?project_id=` | `{cursor, oldest_available}`：廉价探测"要不要拉" |
| GET | `/api/sync/changes?project_id=&since=&limit=&cursor=` | 增量：`{cursor, items:[{type, uid, op, payload, item_rev}], deleted:[{type, uid}], has_more}`；**`gap:true` 表示 `since` 早于流水保留窗口 → 客户端必须改走 snapshot** |
| GET | `/api/sync/snapshot?project_id=&cursor=` | 首次接入/重建：分页全量 + 当时的 `cursor` |
| POST | `/api/sync/push` | 批量提交（见下），**逐条**返回 `{op_id, status: ok|conflict|rejected, item_rev?, server?}`；`rejected.reason ∈ readonly/forbidden/parent_missing/invalid` |

**push 请求**
```json
{ "project_id": 10, "device_id": "d-8f21…", "ops": [
  { "op_id": "uuid-a", "op": "upsert", "type": "api", "uid": "0f5c…",
    "base_rev": 4201, "payload": { "…全量字段…" } },
  { "op_id": "uuid-b", "op": "delete", "type": "group", "uid": "aa11…", "base_rev": 4190 } ] }
```
- **拓扑序要求**：ops 按"父先子后"提交（先 group 后其下 api）；父缺失的服务端返回 `rejected.parent_missing`，客户端稍后重试（§5.9-D）。
- **secret 语义**：payload 中 secret 变量只带 `has_value`（P0）；P1 起"具备项目 update 权限"才回传/接受明文；**支持"值不变"标记**（客户端没拿到明文时不误清空服务端值）。

### 4.3 时序

**首次接入（新设备）**：`登录（PAT）→ 选项目 → snapshot 分页 → 写本地文件 → 记 cursor`。
**首次接入（本地已有文件，如 git clone 的集合）**：按 `uid` 配对——两端都有 → 比基线；本地有服务端无 → 当 create 推送；**文件缺 `uid`（Bruno 手写）→ 首次纳入时分配 uid 并 create**；同名不同 uid → 按新建处理（不猜、不合并），UI 提示可能重复。

**日常一轮（顺序固定：先 pull 后 push）**
```
1 本地扫描：文件内容 hash 变化 → 标 dirty（含外部 git checkout 造成的改动）
2 GET /sync/state → {cursor}
3 cursor > 本地 → GET /sync/changes?since=本地cursor（gap? → 走 snapshot）
4 应用到文件：upsert 覆盖/新建；delete → 移入 .trash/；冲突 → .conflicts/ + 提示
5 收集 dirty → POST /sync/push（拓扑序；op_id 幂等）→ 逐条结果
6 写回 meta.base_rev / item_rev / cursor；失败保持 dirty 并指数退避
```
每项目一个本地锁（防两窗口同时 push）。

### 4.4 冲突策略（v1：LWW + 冲突副本）

- 判定：客户端 `base_rev` ≠ 服务端条目当前 `last_change_id` ⇒ `conflict`（**比较条目版本号，不是时间戳**——时间戳有同毫秒重复与时钟权威问题，见 §5.9-B）。
- 处理：**服务端版本落回原文件；本地版本另存 `.conflicts/<name>.conflict-<device>-<ts>.yml`**；UI 三选一：以本地覆盖 / 以远端覆盖 / 保留副本。
- 字段级三方合并列为后续增强（依赖 T06 字段级 diff）。

### 4.5 删除、回收站与分组级联（依据现有实现）

- **服务端删分组只软删组本身，子接口保留且 `group_id` 悬空**（`content.go:56-65`；`RestoreApis` 需"补齐已删除分组祖先链"也佐证，`content.go:145-163`）。
- 因此同步协议约定：**组删除只产生组的 tombstone，子项保持活跃**；客户端收到组 delete → 移除该组的 `folder.yml`、**保留目录与子文件**，子项呈现为"未分组"（与 Web 行为一致）；组还原（回收站）→ `folder.yml` 恢复，目录语义回来，**文件不搬家**。
- **`.trash/` 恢复 = 重新创建**：用户把文件移回集合 → 同步引擎 push upsert → 服务端按"软删行可重建"的既有唯一索引约定恢复（`is_deleted=0`），并产生新流水。**不存在"复活 bug"**——这是用户主动行为，协议天然支持。
- 服务端**不再**为同步额外做"级联软删子项"（避免与 Web 行为分叉）；若未来改为级联，则每个子项各写一条 tombstone 即可，协议不变。

### 4.6 关联模型：单机 / 联机（**按本地集合设置**，2026-09-27 修订）

> 用户疑问：「是否应该按项目设置为单机或者联机？本地项目选择关联服务端项目，就完全跟着服务器同步；另外的项目保持本地。」
> **采纳，并据此修正原设计**：`单机/联机` 是**本地集合的属性**（绑定关系写在集合的 `opencollection.yml` 的 `sync:` 段），**不是服务端项目的属性**。一个客户端可同时存在多个集合：有的关联公司服务端项目、有的纯本地，互不影响。
> **随之简化**：原设计放在服务端的 `sync_policy` 三档**取消**——细看它描述的其实是"**客户端的同步方式**"（自动双向 / 只推不自动拉 / 只读镜像），放服务端是放错了边；服务端真正需要表达的只有"**能不能写**"，而这由**权限位**（已有）表达即可，另加一个可选的显式开关兜底。

#### 4.6.1 两层开关，各自归位

| 层 | 属性 | 谁设置 | 决定什么 |
|---|---|---|---|
| **本地集合**（`opencollection.yml` 的 `sync:` 段） | `linked`（未关联 = 纯单机）+ `mode: auto \| manual \| mirror` | 用户在客户端设置 | 这个集合**要不要同步**、**怎么同步** |
| **服务端项目** | 权限位 `PermXxx`（已有）+ 可选 `client_write_enabled` 开关 | 项目负责人 | 关联之后**允许做什么**（能不能推、能不能拉） |

> 心智模型与 **git 的 `origin`** 完全一致：一个仓库可以没有 remote（纯单机），也可以有 remote 并决定 pull/push 的节奏；remote 的凭据（PAT）各人自己的，绝不进集合文件。

#### 4.6.2 客户端 `sync.mode`

| mode | 行为 | 适用 |
|---|---|---|
| `auto`（**新关联默认**） | 自动双向：事件/定时驱动的 pull + push，冲突走 `.conflicts/` 副本流程 | 团队协作、多设备 |
| `manual` | push 自动（本地改动即提交），**pull 仅手动**（「拉取」按钮 + 拉取前预览将发生的变更） | 想自主控制"什么时候吸收服务端变更" |
| `mirror` | **只拉不推**：本地 = 服务端项目的只读镜像/缓存；本地编辑禁止或仅存草稿不落盘 | "完全跟着服务器走"的查阅形态（测试/交付/移动端查阅） |
| （未关联） | **纯单机**：无 PAT、无任何服务端交互；互操作走文件与 OpenAPI/Postman 导入导出 | 个人实验、示例集合、离线演示 |

#### 4.6.3 有效行为矩阵（本地 `mode` × 服务端）

| 客户端 `mode` \ 服务端 | 有 update 权限 | 无 update 权限（只读成员） | 项目开启「禁止客户端写入」 |
|---|---|---|---|
| `auto` | **双向同步** | 自动拉；推送被拒（`rejected.forbidden`，UI 置灰推送入口） | 同左（`rejected.readonly`） |
| `manual` | 手动拉 + 自动推 | 手动拉；推送被拒 | 同左 |
| `mirror` | 只拉 | 只拉 | 只拉 |
| 未关联 | 纯单机 | 纯单机 | 纯单机 |

> **权限不足 ≠ 出错**：`rejected.forbidden` 是正常路径，客户端把对应条目标记只读并说明原因。

#### 4.6.4 绑定 / 解绑 / 换绑

- **绑定**：客户端「连接服务端项目」→ 选 `server_url` + PAT + 项目 → 选 `sync.mode` → 初始对齐（空目录 = 拉快照；已有文件 = 按 `uid` 双向对齐，见 §4.3）→ 写入 `opencollection.yml` 的 `sync:` 段。
- **解绑**：移除 `sync:` 段 ⇒ 集合变纯本地，**文件全部保留**（服务端数据不动；已推上去的历史仍在服务端）。
- **换绑**：先解绑再绑另一个服务端项目（`uid` 不变 ⇒ 服务端视为新项目里的 create）。
- **团队共享配置**：`server_url` / `project_id` / `mode` 可以随集合文件提交（同事 clone 后只需填自己的 PAT 即可完成绑定）；**PAT 与 secret 绝不入集合文件**（各人 keychain / `*.secrets.yml`）。

#### 4.6.5 对改造清单的影响

- **原 S14（服务端 `sync_policy` 三档）取消**；服务端只需：权限位（已有）+ 可选 `project.client_write_enabled`（默认 true；关闭后 `/sync/push` 对该项目一律 `rejected.readonly`——给负责人一个"一键禁止所有客户端写"的显式开关，比收权限位更直观，且不影响 Web 内权限）。
- **保留** S7/S8（PAT 与设备标识）：无论什么 mode，服务端都要知道**谁在同步**（审计与冲突副本命名）。
- **论证保留（为什么"只做上传"仍省不下协议）**：`uid`（否则改名/移动/离线新建会重复建条）、**tombstone**（否则离线端把已删条目"复活"）、条目级基线（否则静默覆盖他人改动）——三样与 mode 无关，都必须有；可省的只有自动回灌，而那已经变成 `mode=manual`。

### 4.7 secret 同步与加密（方案 B）

- 服务端：`pkg/crypto`（AES-256-GCM，nonce 12B，落库 `v2:base64(nonce||ct||tag)`）；**历史明文行无前缀按明文读**（`0011_secret_encrypt` 不改列）。配置 `SECRET_ENCRYPT_KEY`：**空 = 不加密且拒绝写 secret**（⚠️ 该名曾被已废弃的 datasource 功能使用，部署务必用新密钥）。
- 读路径：默认一律掩码 + `has_value`；仅"具备项目 update 权限者 + 显式索取"解密并 `recordOp`（只记变量名）。解密失败 → 空值 + "无法解密"标记，不 panic。
- 客户端：明文只写 `environments/<env>.secrets.yml`（git-ignored）或 OS keychain；普通环境文件保留 `secret: true` 占位；secrets 文件缺失 → 按"空值"渲染并提示「未同步密钥」。
- 后续升级 E2EE：密文再加一层前缀，**不改表结构**。

### 4.8 逐场景走查

**一条接口的九步生命周期**

| # | 谁 | 动作 | 数据 |
|---|---|---|---|
| 1 | 客户端 | 离线新建 | 文件写 `meta.uid: 0f5c…`；索引标 dirty |
| 2 | 客户端 | `GET /sync/state` | ← `{cursor:4200}`；与本地相等 ⇒ 无需拉 |
| 3 | 客户端 | `POST /sync/push` | `{op_id:"uuid-a", op:"upsert", type:"api", uid:"0f5c…", base_rev:null, payload}` |
| 4 | 服务端 | 按 `ext_uid` 查：无 ⇒ create（分配 id、写 ext_uid、写流水） | → `{status:"ok", item_rev:4201, update_time}` |
| 5 | 客户端 | `meta.base_rev = 4201`，状态转 clean | 基线只来自服务端 |
| 6 | 设备 B | `GET /sync/changes?since=4200` | ← `items:[{type:"api", uid:"0f5c…", op:"upsert", payload, item_rev}]` |
| 7 | 设备 B | 按 uid 找文件：无则**新建文件**（按 group/name 渲染路径，见 §5.9-I 的两阶段应用），有则更新 | B 的 cursor 推进 |
| 8 | 冲突 | B 改了未推、A 也改了 ⇒ B push 带旧 `base_rev` | 服务端 `base_rev ≠ last_change_id` ⇒ `conflict` + 服务端版本 |
| 9 | 冲突处理 | 服务端版本落回原文件；B 的版本进 `.conflicts/` | UI 三选一 |

**删除的传播**
```
A 删除        → push {op:"delete", uid} → 服务端软删 + 流水 op=delete
B（离线中）   → pull 看到 delete → 文件移入 .trash/（不物理删）
              → 若 B 同时又改了它并 push → 服务端以 delete 为准（tombstone 阻止复活）
Web 回收站还原 → is_deleted=0 + 流水 upsert → 各端从 .trash 恢复/重建
```

**场景速查表**

| 场景 | 本地 | 同步 | 服务端 | 对端 |
|---|---|---|---|---|
| 新建接口（离线） | 文件 + uid + dirty | push(upsert, base=null) | create | pull → 新建文件 |
| 编辑接口 | 自动保存写文件 | 防抖后 push | update | pull → 覆盖（本地 clean 无提示） |
| **重命名请求** | 文件改名、`title` 变 | push(upsert) | update title | pull → **改名本地文件**（不是新建） |
| **移动分组** | 文件移动、`group_id` 变 | push(upsert) | update group_id | pull → 移动文件 |
| 调整组内顺序 | 写回 `info.seq` | 一批 push（防抖合并） | 批量 update | pull → 重排 |
| 删除接口 | 移入 `.trash/` | push(delete) | 软删 + tombstone | pull → 移入 `.trash/` |
| 删除**分组** | 移除 `folder.yml`，**目录与子文件保留** | push(delete, group) | 只软删组（**现状**，§4.5） | pull → 组目录消失，子项呈"未分组" |
| 回收站还原（Web） | — | pull 到 upsert | is_deleted=0 | 恢复 `folder.yml`/文件 |
| 两处都改同一条 | dirty + 旧基线 | push → `conflict` | 返回服务端版本 | 原文件=服务端版 + 本地进 `.conflicts/` |
| 两处新建同名不同物 | 各自新 uid | 两次 create | 两条记录（**不合并**） | UI 提示可能重复 |
| 文件被 git checkout 覆盖 | hash 变 ⇒ dirty | 与远端不同则 push；相同则仅更新索引 | 视基线 | — |
| 长期离线（超过流水保留窗口） | dirty 积压 | changes 返回 `gap:true` → **走 snapshot 重建对齐** | oldest_available | — |

**客户端会话模型（多 TAB + 默认直接可编辑）**——这是选"完全分离"的直接原因，单列规则：

| 规则 | 说明 |
|---|---|
| draft 与文件分离 | 编辑发生在内存 draft；`Send` 用当前 draft，**绝不因未保存阻塞** |
| 自动保存（防抖 ~500ms；关闭 tab/失焦/发送前 flush） | 与"文件=真相源"一致，避免显式保存成为测试摩擦 |
| 变更判定用内容 hash | 自动保存会频繁刷 mtime ⇒ 只有**内容 hash 变化**才进 push 队列（2s 合并批量） |
| 自写回环抑制 | 自动保存触发的 fsnotify 事件需标记"本进程写入"，避免自己重载覆盖 draft |
| 外部改动保护 | 文件被外部修改且有未落盘编辑 ⇒ 询问：重新载入 / 保留我的编辑（存冲突副本） |
| pull 冲突保护 | 不静默替换编辑器内容，走冲突流程 |
| tab 与路由解耦 | tab 驱动内容；深链（从历史/搜索打开 uid）= 新 tab |
| 会话恢复 | 打开的 tab 列表 + 草稿持久化到本地索引，重启恢复 |
| 关闭 tab 语义 | 自动保存兜底 ⇒ 无"是否保存"确认；仅写盘失败时降级提示 |

## 5. 同步设计评审（2026-09-27：9 项发现，2 项已采纳进协议）

> 对 §4 的批判性自检。**总体判断：方向合适**——条目级 + 变更流水 + tombstone + 条目基线，是"文件优先 + 多设备"场景的标准解法（与 Obsidian/Bruno 生态的同步思路一致），且与现有"软删 + 乐观锁 + 唯一索引排除软删行"天然衔接。但按"两台设备 + Web 三方并发 + 长期离线"推演，发现以下问题；**R1/R2 是设计修正（已改写进 §4），R3–I9 是必须补进实现清单的缺口**。

| # | 发现 | 对策 | 状态 |
|---|---|---|---|
| **R1** | **冲突基线用时间戳不可靠**：同毫秒两次写会漏判冲突；客户端时钟不可信，若用本地时间做基线则永远冲突 | **基线改用条目版本号**：实体加 `last_change_id`（= 该条目最近一次 change_log 的 id，严格单调），push 带 `base_rev` 与之比较；`update_time` 保留给 UI | ✅ 已采纳（§4.1/§4.2/§4.4） |
| **R2** | **删除分组的级联语义未定义**：现状只软删组、子项 `group_id` 悬空（`content.go:56-65`）；若协议想当然"删组=删子项"，会产生孤儿文件或错误级联 | **按现状定义协议**：组删除只 tombstone 组；子项保持活跃、呈现为"未分组"；客户端**不搬家**（只删 `folder.yml`）；还原即恢复。若未来改级联，逐子项写 tombstone，协议不变 | ✅ 已采纳（§4.5） |
| **R3** | **游标/revision 的并发有序性**：自增 id 的**分配顺序 ≠ 提交顺序**（事务 A 拿 id=100、B 拿 id=101，B 先提交）→ 增量可能漏读 | SQLite 单写（现部署）天然串行无问题；**Postgres/高并发**：写 change_log 前对项目行 `SELECT … FOR UPDATE`，使"分配与提交"有序。**多拉无害、漏读危险**——禁止用"本次最大 id"当游标的乐观写法 | 列入 S3 实现要点 |
| **R4** | **change_log 无限增长 + 长期离线设备漏变更**：流水一旦清理，`since` 之前的变更丢失 | `changes` 返回 `oldest_available`；`since < oldest_available` ⇒ `gap:true` 强制走 snapshot。清理策略：保留 ≥ 90 天或 ≥ 10 万条（取大） | 列入 S4/S6 |
| **R5** | **push 幂等需要存储**：光靠"约定 op_id"不防重复 | `sync_op` 表（`op_id` 主键 + 结果摘要，保留 30 天）；重复 op_id 直接返回上次结果 | 列入 S4 |
| **R6** | **push 的拓扑序**：父分组未建时子条目 upsert 会失败 | 客户端按"父先子后"排序 ops；服务端父缺失返回 `rejected.parent_missing`（客户端重试） | 列入 S4/C7 |
| **R7** | **pull 落盘的顺序依赖**：请求文件的目录由分组渲染，分组未拉到时无法落盘 | 客户端**两阶段应用**：先写内存模型，组齐后统一落盘；或按"先 group 后条目"排序应用 | 列入 C2 |
| **R8** | **冲突副本会被当成普通文件同步**（`.conflict-*.yml` 带 uid 的话会被推回去） | 副本放 `.conflicts/`（监听与同步引擎**忽略**），文件头写 `meta.conflict_of: <uid>`，**不带可同步 uid** | 列入 C2 |
| **R9** | **文档正文里的图片 URL 离线失效**：Markdown 引用 `/uploads/...`，离线打不开 | 渲染时做映射：按文档引用的 sha256 清单从 `assets/` 取本地文件；拉取文档时**顺带按需拉附件** | 列入 C5/S11 |

**三个"好消息"（现有设计与协议天然契合）**：① 软删 + "唯一索引排除软删行" ⇒ **`.trash/` 恢复 = 合法重建**，无需额外机制；② 现有 `ensureNotStale` 已是条目级基线比较的单条版，批量 push 可直接复用其逻辑；③ Web 端 CRUD 与客户端 push 走**同一套 repository 写路径**，change_log 一处落点即可覆盖两个入口。

## 9. 附录

### 9.1 为什么 git 不能当同步通道

| 场景 | git 方案 | 本协议 |
|---|---|---|
| 两设备改同一集合的不同接口 | 可 merge | pull 增量 + push，无冲突 |
| 同一接口两人各改一半 | 文本冲突人工解 | 条目级冲突 → 副本 + 一键取舍 |
| 服务端作为团队真相源 | git 仓库成为真相源，权限/回收站/审计失效 | 服务端仍是权威副本与权限中心 |
| 删除同步 | 文件消失≠知道"谁删的" | tombstone + `.trash/` |
| 大附件 | 二进制反复入库 | `assets/<sha256>` 按需拉取 |

git 仍可作为**用户侧备份/分支探索**手段。

### 9.2 专项：UI 复用 vs 分开（结论：完全分离）

实测：现有 `*.vue` 共 **9159 行**，其中客户端**直接可用仅 ~579 行（6%）**、**改造后可用 ~3620 行（40%）**、**不需要 ~4960 行（54%）**（项目概况/变量页/分享/公共属性/文档页/备忘/用户管理/通知…）。**且客户端最核心的能力在现 UI 里是零**（发送/响应/历史/断言/Cookie/多 TAB/同步状态），无论选哪条路都要新写。
用户最终以两条结构性需求拍板**完全分离**：① **多请求 TAB**（现 UI 是路由驱动单内容区）；② **默认直接可编辑**（现 `ApiDetailView` 是文档优先 + `editing` 单例两态）。这两条使 `ApiDetailView`(1001)/`AppLayout`(407) 从"改造后可用"降级为"需重写"、`SectionTree`(935) 降为"交互参考"。
**共享边界 = Go 纯逻辑 `pkg/*` + i18n 文案（407 key 中约 128 双端共用）+ 小展示组件直接复制（~579 行，不建跨仓库组件包）**。

### 9.3 专项：共享库分层（L1/L2/L3）

- **L1 Go 纯逻辑** `pkg/*`：必须共享，P0.5 抽取（"只搬不改语义"，原单测原样通过）。
- **L2 契约类型 + API client**：`packages/api-client`，由契约生成，性价比最高（防类型/字段漂移）。
- **L3 UI 组件 + i18n + tokens**：**同仓库 workspace 抽包为目标形态，但按"两次法则"在 P3 后按需收口**——客户端工作台形状刚定，现在抽象 UI 库=在形状未定型时猜接口。
- L3 边界：可直接进（`MethodTag/JsonBlock/TablePager/EmptyHint/RepoMark`）；小改可进（`VarText/VarBadge/EnvPicker` → props 化）；**不进**（页面级组件）。四条硬约束：无 store/router/HTTP 依赖、i18n 注入、导出 design tokens、naive-ui 作 peer 依赖锁版本。

### 9.4 与现有规划的关系

- 不依赖也不复用现有前端代码；T17 i18n 成果降级为 **UX 与文案基线**。
- **T06 字段级 diff** 是"冲突字段级合并"（后续增强）的天然前置；**T07 发布状态**与本方案无强耦合。
- 服务端请求代发（S12）只服务 Web Try it；客户端执行与它互不影响。
- **新增前置**：`pkg/*` 抽取与契约冻结（P0.5）必须先于客户端内核动工。
