## 二、结论与定位

1. **不缺文档编辑能力，缺的是「契约治理 + 自动化测试」**：文档已能在线调试（RM-01）；但变更不可追溯；脚本断言有了，却没有集合运行器和 CI 出口。
2. **不建议追 Apifox 的全量功能**：性能测试、安全扫描、复杂审批、全套 SSO 与长尾协议投入大，会稀释「轻量」定位。
3. **应强化差异化**：本地文件为真相源、离线可用、双向同步、MCP/AI。路线图优先做能放大这三点的能力：Web Try it、集合运行器/CI、契约校验、AI 辅助。

## 五、批次 1（1–2 周）：让文档「能用」

### RM-01 Web 端 Try it 在线调试

- **目标**：在 Web 接口详情页直接发请求，复用项目环境与变量，减少切到 Postman/Apifox。
- **范围**：
  - 服务端新增受权限保护的请求代理（建议 `POST /api/proxy/send`）：方法、URL、请求头、查询参数、Body、认证、环境 ID。
  - 复用 `resolveTable` 渲染变量；只读成员可用，但明文 secret 不进入响应。
  - 安全：SSRF 防护（禁回环/内网，或按配置白名单）、超时、响应大小上限、重定向策略、审计日志。
  - 前端：接口详情「调试」面板（请求预览、发送、状态码/响应头/响应体、复制为 cURL）。
- **验收**：GET/POST/PUT/DELETE 与 JSON/form/raw 可用；环境变量替换正确；只读成员可用但看不到明文 secret；内网地址被拒；审计有记录；单测 + 一条 e2e。
- **依赖**：变量/环境、权限位（已完成）。**成本**：中。**状态**：已完成（2026-10-23）。

**落地说明（2026-10-23）**

- 服务端新增 `POST /api/v1/proxy/send`（仅 v1，避免历史前缀继续膨胀）：`service/proxy.go` 负责权限校验、`resolveTable/renderVars` 渲染、认证、表单/JSON 正文与查询参数合并；`handler/proxy.go` 限制请求体 2 MB。
- SSRF 防护：仅 http/https、禁 URL 内嵌账号；自定义 `DialContext` 解析并校验全部 IP（回环/内网/链路本地/组播/保留段），再直连已校验 IP（防 DNS rebinding）；禁环境代理；最多 5 次重定向；15s 超时；响应 5 MB 上限。
- 无明文权限的成员仍可使用调试，但敏感占位符原样保留（不把 secret 发往任意目标）；有权限者正常渲染。审计只记方法、主机、路径与敏感变量名。
- 前端新增 `components/TryItPanel.vue`，接口详情 `.req-ops` 增加「调试」入口；面板复用当前表单与环境选择，支持请求头/查询/请求体/认证编辑与响应查看。
- 回归：`TestProxySendRendersAndGatesSecrets`、`TestProxySendRejectsSSRFAndBadScheme`、`TestIsBlockedProxyIP`、`TestProxyRouteVersionedOnly`、`TestProxySendParamError`；契约文档 `doc/api_docs/proxy/proxy_send.yml`。

### RM-02 集合运行器 + CLI CI

- **目标**：把「文件即集合」变成可自动化的测试资产。
- **范围**：
  - 扩展 `cmd/clientctl`：`run <dir> --env <name> --filter <tag> --reporter json|junit --bail --timeout`。
  - 按目录顺序运行请求，执行脚本/断言，汇总成功/失败/跳过，失败退出码非 0。
  - 变量提取与链式传递（响应 → 运行时变量）；后续再补 CSV/JSON 数据驱动。
  - 桌面端「运行集合」面板复用同一执行层与报告结构。
  - 提供 GitHub Actions / GitLab CI 示例。
- **验收**：一条命令跑完集合；JUnit 可被 CI 解析；失败能定位到请求与断言；顺序稳定；e2e 夹具覆盖成功/失败/超时三类。
- **依赖**：现有 runner/script（已完成）。**成本**：中-大。**状态**：待做。

### RM-03 生产阻塞项（审核 H-14～H-17）

- **目标**：先修正确性/安全问题，再叠加新功能。
- **范围**：
  - H-14：引入迁移执行器（`golang-migrate` 或 `goose` + `embed.FS`），让 `migrations/{sqlite,postgres}` 真正执行；补 up/down 成对校验与 Postgres CI。
  - H-15：`user_info` 改为 name、email 两个独立局部唯一索引；登录重名时拒绝并提示。
  - H-16：`AssignBug` 三步写库包事务；`Notify` 改 best-effort。
  - H-17：导出分页拉全量，或在响应中返回 `truncated` 标记，杜绝静默丢第 201 条之后的接口。
- **验收**：迁移 up/down 往返通过；同名不同 email 注册/改名被拒；AssignBug 失败可回滚；>200 接口导出完整或明确标记。
- **成本**：中。**状态**：已完成（2026-10-23）。

**落地说明（2026-10-23）**

- **H-14**：新增 `server/migrations/embed.go`（`embed.FS` 打包）；`internal/database` 改为版本化执行器（`schema_migrations`、单版本单事务、SQL 分句器、up/down 成对与两方言一致性校验、已有库自动基线化（基线化/0019 前检查同名与重复邮箱）、`MigrateDown`）。生产 `MigrateRelease` 只跑迁移，开发/测试 `Migrate` 再 AutoMigrate 兜底；补 `0010` down、`0018_schema_parity`（file.hash/size/mime + 索引名统一）、`0019_user_name_email_unique`；新增 `TestMigrationsMatchModels` 拦截模型/迁移漂移，`.github/workflows/ci.yml` 增加 `migrate-postgres` job。

- **H-16**：`AssignBug` 的「改指派人 + 写流转记录」包进 `repo.Transaction`；通知改 best-effort（失败只记日志）。测试用 SQLite 触发器分别验证「通知失败不回滚」与「流转失败整体回滚」。

## 九、明确不做（保护定位）

1. **全量性能/压力测试、安全扫描**：投入大，与「轻量文档协作」定位冲突；有客户需求再单独立项。
2. **复杂审批流/多级评审**：先用评论 + 通知满足协作，不引入工作流引擎。
3. **SSO/OIDC/LDAP 全家桶、多租户组织**：先做单点 OIDC（RM-16），不做组织计费体系。
4. **MQTT/Socket.IO 等长尾协议**：按真实需求逐个加，不一次铺开。
5. **实时多人协同编辑**：成本极高；现有乐观锁 + 冲突副本已覆盖主要场景。
6. **把 Web 前端改成与客户端同构**：既定「两套代码」的边界不打破。

## 十、执行约定与完成定义

- **跨仓顺序**：涉及共享契约时，先改 `api-doc-go-share` 并打 tag → 两端 `GOWORK=off go get` → `bash scripts/share-version.sh` 通过。
- **完成定义（DoD）**：
  1. 代码 + 单测/回归；涉及 UI 的补 `data-testid` 与 i18n key；涉及接口的补 `doc/api_docs/**`。
  2. 客户端跑 `bash scripts/check.sh`；服务端跑 `bash scripts/check.sh --skip-build`；涉及同步/备份的补 `-race` 用例。
  3. 更新本表的「状态」与「落地记录」，重要行为变化同步到 `doc/项目进度.md` 或同步现状文档。
  4. 每项独立可发布，不做大爆炸重构；破坏性协议变更必须升 `syncapi.Proto`。
- **排序原则**：正确性/安全 > 消费侧可用性 > 契约治理 > 协作 > 生态扩展；每批结束后复盘一次，再调整下一批。
