# 项目开发规范

> 本规范用于指导 **Go + Vue3 + SQLite/可选 PostgreSQL** 版 api-doc 的重构开发，
> 面向「人 + AI 协作」编写：所有约束尽量可判定、可自检。
> 现有功能与接口清单见 [功能清单.md](./功能清单.md)，迁移方案见 [重构方案.md](./重构方案.md)。

## 0. 技术栈总览
| 层 | 选型 | 版本/说明 |
| --- | --- | --- |
| 语言 | Go | 1.26.7 |
| Web 框架 | gin | 路由 + 中间件 |

## 1. 目录规划

### 1.1 仓库根
```
api-doc-go/
├─ api_docs/          # 接口文档（按功能分组，一接口一 yml）
├─ doc/               # 设计与规范文档（本目录）
├─ server/            # Go 后端
├─ web/               # Vue3 前端
└─ database/          # 初始化 SQL / 种子数据
```

### 1.2 后端 `server/`
```
server/
├─ cmd/server/main.go        # 入口：装配 config/db/router，启动 http
├─ internal/
│  ├─ config/                # 配置加载（env / yaml）：端口、DB 驱动、DSN、JWT secret
│  ├─ model/                 # GORM 实体（对应数据表）
│  ├─ dto/                   # 请求/响应结构体 + 校验 tag（按操作拆分）
│  ├─ repository/            # 数据访问层（仅 CRUD，不含业务）
│  ├─ service/               # 业务逻辑层（事务、校验、编排 repository）
│  ├─ handler/               # HTTP 层（解析请求→调 service→统一响应）
│  ├─ router/                # 路由注册，按模块分组
│  ├─ middleware/            # auth、project-permission、cors、recover、logging
│  └─ pkg/                   # 无业务依赖的通用包（response、errcode、page、jwt、logger）
├─ migrations/               # 数据库迁移（sqlite / postgres 两套）
└─ go.mod
```
> 依赖方向（单向，禁止反向）：`handler → service → repository → model`；`dto` 横切在 handler/service 边界；`pkg` 被所有层复用但不依赖业务层。

### 1.3 前端 `web/`
```
web/
├─ src/
│  ├─ api/                   # 接口调用，按模块一文件（api.ts / project.ts ...）
│  ├─ router/                # 路由与守卫
│  ├─ stores/                # Pinia，按模块（user.ts / project.ts ...）
│  ├─ composables/           # 组合式函数 use*（useAuth、usePagination ...）
│  ├─ views/<module>/        # 页面，按业务模块建目录
│  ├─ components/            # 通用/业务组件
│  ├─ types/                 # TS 类型与接口契约
│  ├─ utils/                 # 纯函数工具
│  ├─ assets/                # 静态资源
│  └─ main.ts / App.vue
├─ .env.development / .env.production
└─ vite.config.ts
```

### 1.4 接口文档 `api_docs/`
```
api_docs/
├─ _example/                 # 现有模板（get/post/put/delete/post_action）
├─ user/  project/  group/  api/  doc/  bug/
├─ field-mapping/  data-dict/  operation-log/  file/
└─ common/                   # 通用错误码、鉴权、分页约定
```
- 一个接口 = 一个 yml 文件；文件按「模块目录 + 动作」命名，如 `api/api_create.yml`、`api/api_list.yml`。

## 2. 模块划分
以现有 `功能清单.md` 为准，后端 service/handler、前端 views、api_docs 三处保持**同名同粒度**，便于对照。

| 模块 | 职责 | 后端包 | 前端视图 | api_docs 分组 |
| --- | --- | --- | --- | --- |
| auth/user | 注册、登录、token、资料、改密、用户管理 | `user` | `views/user` | `user` |
| project | 项目 CRUD | `project` | `views/project` | `project` |
| member | 成员、负责人、退队、项目权限 | `project`（子域） | `views/members` | `project` |
| group | 多级分组树、排序、类型 | `group` | `components/group` | `group` |
| api | 接口文档 CRUD、软删恢复、检索、**OpenAPI(yaml) 导入展示** | `api` | `views/apiPage` | `api` |
| doc | Markdown 文档 CRUD、浏览/点赞、置顶 | `doc` | `views/docPage` | `doc` |
| bug | Bug 提交/指派/状态/列表 | `bug` | `views/bug` | `bug` |
| field-mapping | 字段字典，接口返回参数自动回填 | `fieldmapping` | `views/fieldMapping` | `field-mapping` |
| data-dict | 外部库连接、读表/结构、导出 | `datadict` | `views/dataDict` | `data-dict` |
| operation-log | 操作审计记录与查询 | `oplog` | `components/operationLog` | `operation-log` |
| file | 图片/文件上传 | `file` | （内嵌） | `file` |

### 2.1 横切能力（不属于单一业务模块）
- **统一响应**：`pkg/response` → `{ code, msg, data }`；HTTP 恒 200（沿用旧约定）。
- **错误码**：`pkg/errcode`；至少保留 `200 成功`、`34 未登录/过期`（前端据此跳登录）、`22 参数错误`。
- **鉴权中间件**：解析凭证 → 注入当前用户；旧版为 query/body `token`，新版建议 JWT（`Authorization: Bearer`），二选一见 §6.1。
- **项目权限中间件**：按 `projectId` + 当前用户校验 CRUD 权限。
- **分页**：`pkg/page`，统一入参 `page_num/page_size`，出参 `pagination{pageNum,pageSize,total,pageTotal}`。
- **软删除**：全模块统一 `is_deleted`（见 §6.3）。

## 4. 开发要求（人与 AI 都要能看懂）
> 原则：**小而专、命名即语义、控制流浅、显式契约**。以下为硬性可判定约束。

### 4.1 通用
1. 一个函数/方法只做一件事；名称能回答「它做什么」，避免 `handle/process/doData` 类空泛名。
2. 魔法值改为命名常量或枚举；状态、类型集中定义（如 `enum` / `const`）。
3. 公共函数/接口/数据结构必须带注释：**用途、参数、返回、错误、副作用**（AI 与新人都靠它建立契约）。
4. 提交前自检：无死代码、无未使用导入、无注释掉的旧逻辑、命名一致。
5. 注释解释「为什么」，不复述「做了什么」。

### 4.2 后端（Go）
1. **函数规模**：单函数建议 **≤ 50 行**，**≤ 3 层嵌套**；超出则拆分子函数（拆后命名仍具体）。
2. **参数个数**：位置参数 **≤ 4 个**；超过时改为传**参数结构体 / Options**，禁止长参数列表。
3. **签名约定**：`func Xxx(ctx context.Context, req *dto.XxxReq) (*dto.XxxResp, error)`；
   - `context.Context` 一律作为**首参**；
   - 返回值遵循 `(result, error)`，不返回 `(nil, nil)` 掩盖错误。
4. **错误处理**：不吞错；用 `fmt.Errorf("...: %w", err)` 包装传播；对外错误经统一 `errcode` 映射，内部错误写日志。禁止 `panic` 做常规控制流（仅启动期致命错误可用）。
5. **分层职责**：
   - `handler`：仅解析/绑定请求、调 service、返回统一响应，**不写业务与 SQL**；
   - `service`：业务规则、**事务边界**、编排 repository；对外暴露**接口**（`type Service interface`）便于测试与 AI 替换；
   - `repository`：仅数据访问，**不含业务判断**；
   - `model` 仅表结构，`dto` 仅传输契约，二者不混用。
6. **入参校验**：在 DTO 上用 binding/validator tag 声明（必填、长度、范围、枚举），进入 service 前完成；service 不信任未校验输入。
7. **GORM**：查询用参数化（防注入）；避免循环内单条查询（用 `Preload`/批量）；写操作放事务；统一软删除与时间戳字段。
8. **数据库可移植**：业务 SQL 不写 SQLite/PG 方言差异语句；方言差异只在 `config`/`migrations`/驱动适配层。
9. **命名**：包名小写单词无下划线；导出符号大驼峰、非导出小驼峰；缩写统一大小写（`ID`、`URL`、`HTTP`）。

### 4.3 前端（Vue3 + Naive UI）
1. **写法**：统一 `<script setup lang="ts">` + Composition API，**全量使用 TypeScript**（禁用无类型的隐式 `any`）；接口数据契约在 `types/` 中**手工维护**，**不做**由 api_docs/OpenAPI 自动生成。
2. **组件规模**：单组件建议 **≤ 200 行**（含模板）；超出按「容器/展示」或功能拆子组件；一个组件单一职责。
3. **函数规模**：单函数 ≤ 50 行、≤ 3 层嵌套；可复用逻辑抽到 `composables/useXxx`。
4. **参数个数**：函数位置参数 ≤ 3；选项类传参用**对象**（`function fetchData({ page, size, keyword })`）。
5. **契约显式**：`defineProps` / `defineEmits` 声明类型；子组件不直接改父状态，通过 emit。
6. **状态管理**：Pinia 按模块拆 store；组件不直接改 store state，通过 action。
7. **接口层**：所有请求集中在 `src/api/`，页面不裸调 axios；统一实例在拦截器注入 `token`（与项目上下文），集中处理 `code=34` 跳登录与错误提示。
8. **路由**：受保护页用 `meta.requiresAuth` + 全局守卫；按业务模块组织 `views/` 目录，与后端模块同名。
9. **UI**：Naive UI 按需引入组件；避免全局引入增包体；样式用 scoped。

## 5. 接口文档规范（`api_docs/`）
1. **格式**：沿用 `_example/` 的 yml 结构（`info` / `http` / `settings` / `docs`），一接口一文件。
2. **命名**：`<模块>/<模块>_<动作>.yml`，如 `doc/doc_create.yml`、`doc/doc_list.yml`；动作与后端 handler 一致（create/update/delete/list/detail/...）。
3. **分组**：按 §2 模块建目录；`info.seq` 控制组内排序。
4. **`docs` 必填段落**（供人/AI/前端对接）：
   - 简要描述、请求 URI、请求方式、请求头；
   - 请求参数表（`|参数名|必选|类型|说明|`）；
   - 枚举/约束（如状态、权限枚举、条件约束）；
   - 请求示例 + 响应示例（json）；
   - 返回字段说明表；备注。
5. **一致性**：文档字段命名、错误码、分页结构与 §2.1 约定及后端 DTO 保持一致；接口变更后同步更新对应 yml。
6. **OpenAPI 导入展示（产品能力）**：系统支持导入**标准 OpenAPI 3.x yaml**（`openapi`/`info`/`paths`/`components`），解析后**转为内部接口文档记录落库**（可再编辑），而非只读原样展示；解析失败返回明确错误、整体导入遵循事务（要么全成功要么全回滚）。映射规则：
   - 目标：导入时指定目标**项目**（必选）+ 目标**分组**（缺省用 `info.title` 作为根分组名）。
   - 分组（group）：优先按 OpenAPI tag（`operation.tags`）→ 同名分组；一个 tag 对应一个二级分组。
   - 接口（api）：`paths` 下每个 `(path, method)` 生成一条 api 记录；`operationId`→接口名，`summary`/`description`→备注，`parameters`/`requestBody`/`responses` 分别映射到请求头/请求参数/返回参数与样例。
   - 去重：按 `(project_id, group_id, method, url)` 判定；已存在时按导入策略（跳过/覆盖，默认跳过）处理。
   - 仓库内 `_example/` 的按接口 yml 与对外导入的标准 OpenAPI yaml 为两套用途，互不混用。

## 6. 数据库与迁移规范
1. **可切换方言**：默认 SQLite、可选 PostgreSQL；实体与查询保持方言无关。
2. **主键/自增**：`bigint`/自增主键；外键关系在应用层 + 必要索引维护（`project_id`、`group_id`、`user_id` 建索引）。
3. **软删除**：统一 `is_deleted`（整型 0/1，禁止再用 `varchar` 存布尔）；所有列表查询默认过滤未删除。
4. **时间字段**：统一 `create_time` / `update_time`，类型一致（`datetime` / `timestamptz`，随方言），禁止用字符串存时间。
5. **迁移**：结构变更走 `migrations/`（sqlite + postgres 两套），文件带递增版本号；禁止只改代码不改迁移。
6. **命名**：表名小写复数/语义名（与旧表对齐便于参考），列名 `snake_case`。
7. **历史数据**：**不做**旧项目（MySQL）历史数据迁移；新库由 `migrations/` 全新建表，仅初始化必要种子数据（如超级管理员账号）。旧 `database/mysql.sql`、`sql/dump-*.sql` 仅作字段/关系参考。
